# The Settings Page Plan (the desktop's one settings surface)

Status: PLANNED — not started. Target release: the next semver after the
current working tree (≥ 0.1.16; bump `main.Version` + `main.WebRef` together,
hard rule 9).

THE OWNER ASK (2026-10-26): "Plan for a settings page for hibana's desktop"
with exactly four sections, in this order:

1. **Sync**
2. **Update app** — "check the latest release of github, if there were newer
   version. update."
3. **Login / logout**
4. **fa/en and dark mode / light mode**

This plan follows the repo's laws: the island is generated (`sync-island.mjs`
— never hand-edit), the bridge is an API surface (one transport + a short
allow-list of zero/validated-argument methods), the cloud stays the source of
truth, and the web's own component grammar (native `<dialog>`, the bare-button
CTA, theme-aware + RTL-native CSS) is reused rather than reinvented.

---

## 1. The surface — `#db-settings-dialog`, one dialog, four sections

### 1.1 Why a dialog and not a second route

The island is a single board document (`frontend/dist/index.html`) generated by
`scripts/sync-island.mjs`; every desktop-owned surface so far (sync, logout,
new-project, update) is a native `<dialog>` injected as a seam patch — theme-
aware and RTL-native for free through `components.css` + `rtl.css`. A second
route would need new asset serving, would fight the island's `/kanban` entry
guard, and buys nothing. The settings "page" is therefore a **wide modal**
(`dialog.dialog > form.modal.db-settings-modal`) — the web's own settings page
grammar compressed into the app's modal vocabulary. It opens from the toolbar
gear and reads as a page (grouped sections, not a cramped confirm).

### 1.2 Entry points

1. **Toolbar gear — `#db-settings-button`** (primary): a ghost icon button in
   the toolbar's account zone, placed after the theme toggle and before Sign
   out (`Sync — Refresh — Update pill — Theme — ⚙ Settings — Sign out`).
   Gear glyph (feather `settings` path), `aria-label`/`title` localized, ghost
   on purpose — Sync stays the row's one colored action; Settings is chrome,
   not a CTA.
2. **Tray "Settings…"** (phase 2, optional): a menu item between Open and Quit
   that shows + focuses the window and emits `hibana:open-settings`; the
   controller listens and opens the dialog. Cheap to add later; not required
   by the ask.

### 1.3 The four sections (the owner's order)

```

│  Settings                                            [×]  │   ← nav.settings (pin dict key)
│                                                          │
```

Behavioral laws each section reuses:

- **Sync now** delegates to the exact existing flow: it is a programmatic
  `#db-sync-button` click (or a shared trigger exported from the settings
  controller) — the proven `#db-sync-dialog` round (connect → upload → sync →
  outcome) opens on top of the settings dialog, which closes itself first so
  the modals never stack. Zero new Go code, zero new strings beyond the
  section copy.
- **Check for updates** calls the bound `CheckForUpdates()` (single-flight
  guarded against the apply; 15s GitHub deadline). Outcomes:
  - available → cache the verdict, reveal the solid-green **Update now**
    (the pill's own grammar), which delegates to the `#db-update-button` flow
    (the proven `#db-update-dialog` with the live progress bar and the
    restarting panel);
  - none → "You're on the latest version." (an offline check NEVER claims
    "no update" — the existing honesty rule; transport trouble reads
    "Couldn't reach GitHub — check your connection.");
  - busy → the honest busy line.
  The periodic `updateLoop` (boot + 2h) keeps running untouched; the settings
  row just adds the manual trigger and the idle-time surface the owner asked
  for ("check the latest release of github, if there were newer version.
  update").
- **Sign out** delegates to the existing `#db-logout-dialog` confirm →
  `Logout` binding → reload into the login gate, where entering a new account
  boots its kanban. The settings dialog closes before the confirm opens.
  Signed-out state needs no settings row: the login gate IS the sign-in
  surface (it covers the board; the toolbar is unreachable beneath it).
- **Language** is the new capability — §2 below.
- **Theme** segments through the existing `SetTheme` binding with the tray's
  full 3-state vocabulary (`light | claude-dark | system`), radio-checked off
  the served `data-desktop-theme` attr. This upgrades the toolbar's binary
  flip with the explicit Follow-system choice the tray already offers; the
  toolbar toggle stays as the quick flip (no removal — no surface regression).

All settings-sheet strings are the controller's own EN/FA pair (the
`desktop-update.js` STR pattern — the pin's dictionaries carry no desktop-
settings keys beyond `nav.settings`, which the title rides for free).

## 2. The one new capability — language (fa/en)

### 2.1 The problem

The language is a **server-side user record field** (`users.language_pref`,
multi-device by design — spec §5.8). The island resolves it boot-time only:
`AuthState()` → `window.__hibanaMe()` → `i18n.js apply()` → `html[lang]`,
`dir`, the FA dict lazy-load, Vazir injection, and the `[data-i18n]` sweep.
There is no write path on the desktop, and even the existing `AuthState`
snapshot goes stale: `a.me` is seeded at boot and never re-fetched.

### 2.2 The binding — `SetLanguage(lang string)` (new file `internal/ui/settings.go`)

Mirrors `SetTheme`'s discipline exactly (a validated enum, never free text):

```
SetLanguage("fa")
  1. validate: allow-list {"en","fa"} — anything else is a rejected
     promise (the hostile-input law; same shape as errBadTheme);
  2. PATCH /api/settings  {"language_pref": lang}  through the Go
     client — the SAME session/Origin machinery every write rides
     (this is a server write: Origin on every write, hard rule 5);
  3. on 2xx: update a.me.LanguagePref under a.mu (the AuthState
     snapshot un-stales — __hibanaMe now tells the truth), then
     emit  hibana:lang {lang}  through the shell's emit relay;
  4. resolve {ok:true, lang}.
     On a transport/5xx failure: resolve {ok:false} with the honest
     message — the sheet shows "Couldn't reach hibana.ir — the
     language is unchanged." and the segmented control stays put.
     An offline flip must never claim success.
```

A dedicated binding (rather than a JS-side `hibanaFetch` PATCH) is required
because of step 3 — a fetch-round-trip would leave the Go snapshot stale and
`__hibanaMe` lying to the next `i18n.apply()`; the reload reflex below would
then re-resolve the OLD language. The Go side must own the write, exactly the
way it owns login/logout/theme.

### 2.3 The live flip + the reload reflex (island side)

On `{ok:true}` the settings controller:

1. **Flips the chrome live** for immediate feedback: sets
   `html[lang]`/`html[dir]`, then calls `window.hibanaI18n.apply()` — which
   re-reads the (now-updated) `__hibanaMe`, lazy-loads the FA dict when
   needed, injects Vazir, and sweeps `[data-i18n]`. Every desktop-owned layer
   relabels through its existing `html[lang]` MutationObserver
   (`desktop-update.js` / `-refresh.js` pattern — the settings controller
   carries one too).
2. **Reloads after ~700 ms** (`location.reload()` — the login-chime-delay
   precedent). This is not optional polish: `i18n.js`'s own law is that
   dynamically injected markup is NEVER re-scanned — `devboard.js` renders
   the board's task titles/labels at render time, so a live-only flip would
   leave the BOARD in the old language under a flipped chrome. The Refresh
   round already proved `location.reload()` re-enters the same board
   (`?project=` survives); here it re-renders it fully in the new language.
   The settings dialog closes first so the reload lands on the board, not a
   modal.

### 2.4 Serve-time language stamping (fixes the FA FOUC too)

Today the served document is hardcoded `lang="en"` (the `htmlOpenTag`
constant); FA users get an EN/LTR flash on every boot until the async
`i18n.apply()` resolves — the web solved this with the `hibana-lang`
localStorage read in `boot.js`, but `boot.js` is stripped from the island, so
the desktop has been living with the flash. The settings round fixes it as a
side effect, the same way theme got its zero-JS first paint:

- `InjectShellState(body, authed, themePref, lang)` grows a fourth input and
  stamps `<html lang="fa" dir="rtl" …>` (plus `data-desktop-lang="fa"` for the
  controller) when the live session's `language_pref` is FA;
- `main.go`'s KanbanIndexMiddleware passes `bridge.AuthState().User.LanguagePref`
  (normalized to `en` when unknown/signed-out);
- result: the post-flip reload paints FA/RTL at the FIRST frame, the reload
  reflex of §2.3 is seamless, and every FA boot stops flashing.

## 5. Tests, gates, and the probe

1. `go vet ./internal/... && go test ./internal/...` — the pure-Go core
   (the new settings_test.go included).
2. `GOOS=windows go vet ./...` — the full app, Windows target.
3. `node scripts/sync-island.mjs --ref <pin> --check` — the island drift
   gate: the new layer + patches must be exactly what the script emits.
4. `scripts/probe-settings.mjs` **(new)** — the headless probe, the
   `probe-login`/`probe-logout`/`probe-update` pattern: gear opens the
   settings dialog; the version line renders; Check-for-updates paints each
   verdict; the segmented controls carry the right active states; the
   language flip flips `html[lang]`/`dir` (probe at the DOM level with the
   FA dict loaded); theme segments persist (reload → the served attr).
5. Manual dogfood on a real Windows host (the owner's lane):
   - gear → settings; each section's delegation lands on the proven modal;
   - Check for updates against a live GitHub release (both verdicts);
   - fa → the sheet + chrome flip live, the reload re-renders the board in
     FA + RTL, restart keeps FA (no EN flash);
   - en back → ditto mirrored;
   - Light/Dark/System persist across restart; the toolbar toggle and the
     sheet agree after each flip;
   - Sign out from settings → gate → new account boots its kanban.

## 6. Rollout

One session round (S-numbering continues the repo's log):

1. Go first: `internal/ui/settings.go` + `authinject.go` + `main.go` wiring +
   tests — the bridge is the API contract.
2. The island sync script: the two new emitted files + the three seam
   patches + checksums; run the drift gate.
3. The probe + the vet/test gates.
4. Bump `main.Version` (next semver), keep `main.WebRef` at the current pin
   (no island re-pin needed — the settings layer is desktop-owned, the pin
   does not move), release lane (CI dual artifact + portable zip), README
   status row + worklog entry.

Effort: the Go half is small and precedented (SetTheme's shape); the island
half is the bulk (a new controller + stylesheet, mostly composition of flows
that already exist); the language reload reflex is the only UX-sensitive seam.
No database migration, no new server route, no web-repo change.

## 7. Risks and their answers

- **Stale `a.me` after a language change** → the binding updates it under the
  same mutex `AuthState` reads (test: before/after).
- **Half-translated board after a live flip** → the 700 ms reload reflex
  (i18n.js's dynamic-markup law makes a live-only flip dishonest).
- **FA first-paint flash** → serve-time `lang`/`dir` stamping (§2.4) removes
  it; also improves every FA boot, settings round or not.
- **Modal stacking** (settings → sync/update/logout confirms) → the settings
  dialog closes itself before any delegated modal opens; one modal at a time.
- **Bridge discipline** → one new method, enum-validated, no free text, no
  new transport (the PATCH rides the Go client the login already uses).
